Bellwether: system architecture and data flow

How voter and donation data moves from county and public sources, through jobs that run only when triggered, into Supabase, and out to the Bellwether web dashboard on Vercel and the Expo iOS canvasser app in the same repo.

Built from this repository on 26 Sep 2026 (main at 84e8fbc), plus the descriptions of PRs #18 and #19 for iOS build status. System level only. The security overlay names the kind of each credential and where it is injected, never a value.

Judgment calls

  1. Supabase does more than store data.

    Auth issues the JWT sessions the dashboard uses, and a sign-up trigger creates a profiles row with role canvasser. Row-level security is on every public table: any signed-in user reads, admins write, and note authors edit their own rows. A Storage bucket holds the weekly job's match caches, and there are two Postgres connection poolers and three materialized views. Not in use: Edge Functions, Realtime, or client-side RPC. RLS only guards the REST path. Jobs and most API routes connect straight to Postgres as the owner role, where RLS doesn't apply.

    Evidence: supabase/migrations/ 001, 002, 016, 030, 044, 045 (045 states the owner-role bypass); build/cache_storage.py; no supabase/functions/ or supabase/config.toml.

  2. Bellwether web and the iOS app are two projects in one repo, not one codebase with two build targets.

    The web app is Next.js 15 at the repo root (React DOM, Leaflet), not Expo or React Native. The iOS app is a separate Expo SDK 57 project in apps/canvass-ios with its own package.json, lockfile and CI job. The root ESLint, TypeScript, Jest and .vercelignore configs all exclude apps/, and no import crosses between the two. They share the repo, CI, the database and, once built, the Next.js /api as the app's backend.

    Evidence: apps/canvass-ios/README.md, apps/canvass-ios/app.config.ts (platforms: ['ios']), .vercelignore, tsconfig.json, .github/workflows/ci.yml.

  3. The weekly cron re-pulls and re-matches donations; it doesn't re-run the model.

    refresh_donations.yml runs on 0 5 * * 0 (Sundays 05:00 UTC) and can be run by hand. It restores the match cache, matches FEC and NY BOE filers to voters, loads through a staging table with an atomic swap, refreshes donor totals and party views, and saves the cache. "Scoring" in this job means deterministic donor-to-voter matching (name plus ZIP) and recomputed totals.

    Evidence: .github/workflows/refresh_donations.yml, build/fetch_fec_bulk.py, build/fetch_nyboe.py, build/matching.py, build/migrate_donations_psycopg2.py.

  4. Voter registration has no refresh cadence.

    It was loaded once by a manual migration, and the contact files were one-off loads. Nothing schedules a reload. The model re-scores only when someone runs it with --write. The last write-back was 1 Aug 2026.

    Evidence: build/migrate_to_supabase.py ("one-time data migration"), build/load_boe_contacts.py, model/README.md, model/score_voters.py.

  5. iOS publishing: the EAS dev build is current; TestFlight and the App Store are planned.

    EAS build 4a2a33dc (dev profile, internal distribution) finished and installed on a registered iPhone. Nothing has gone further. The submit profile is empty, no preview or production build is recorded, and release tasks R-04 and R-06 are open. The encrypted store in PR #19 needs a fresh dev build, and the repo doesn't say whether one was made.

    Evidence: PR #18 and PR #19 descriptions, apps/canvass-ios/eas.json, docs/canvass_task_plan.md.

  6. The ML pipeline writes through a direct Postgres URL as the owner role, not the service-role key.

    It reads the URL from the repo-root .env.local (gitignored), or from a master copy outside the repo, and runs on the maintainer's workstation, not in CI. The weekly job (via GitHub Actions secrets) and the web API (via Vercel env) use the same kind of credential.

    Evidence: model/db.py, model/config.py, .env.local.example, lib/db.ts.

  7. Vercel builds and hosts; it doesn't transform data.

    Vercel deploys the root Next.js app through its Git integration on every push to main. Functions are pinned to pdx1 next to the database, and vercel.json sets the security headers. There is no Vercel cron.

    Evidence: vercel.json, .vercelignore, commit 16f7ee5 (a no-code commit pushed to force a redeploy).

  8. Weekly donation refreshes don't reach the served scores.

    The model's donation features stop at the 2024 election-day cutoff in both the training and serving feature sets. A new donation changes the dashboard's donor views, but not turnout_prob or the lean scores.

    Evidence: model/README.md ("Donation features are a known gap").

  9. The iOS app will reach data only through the Bellwether API.

    Spec §11 and task P1-03 plan these controls: sign-in through the API, short-lived tokens in the Keychain, one active device per account, a minimum-version check, and cache wipes. None of it is built yet. Today the app makes no network calls and holds no Supabase keys.

    Evidence: docs/canvassing_mapping_target.md §11, §13, §14a; docs/canvass_task_plan.md P1-03, P1-05, P1-08; apps/canvass-ios/src/.

What the repo can't confirm

  • Which variables are actually set in Vercel, per environment. The table above follows the README, .env.local.example and the code that reads them.
  • Supabase Auth settings, such as whether open sign-up is enabled, email confirmation, and token lifetimes. These live in the dashboard; the repo has no supabase/config.toml.
  • The database role behind the weekly job's secret. The diagram assumes the owner-role URL pattern the repo documents elsewhere.
  • Whether a new dev build was made after the encrypted store landed. The build on the phone predates it.
  • How the election_results table was filled. The dashboard reads it, but no script in the repo writes it.

Not drawn: the legacy static canvass tool in build/ and dist/, which predates the web app and was deployed by an older script.
